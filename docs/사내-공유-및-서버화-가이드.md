# MAPS 사내 공유 · 서버화 가이드

HTML 파일을 사람마다 전달하는 방식에서 벗어나 **URL 하나로 공유**하는 방법과,
그 다음 단계로 **로그인 · 게시판 · Q&A 까지 실제로 동작하게** 만드는 방법을 정리한다.

또한 사내 클라우드(원격 데스크톱 계열)에서 배경 영상이 버벅이는 원인과 대응을 함께 적는다.

---

## 0. 먼저 알아야 할 것 — 지금은 "화면만" 도는 상태다

`index.html` 은 마크업 · 스타일 · 스크립트가 전부 들어 있는 단일 파일이지만,
실제 동작에는 같은 경로의 백엔드 API 가 필요하다. **이 저장소에는 백엔드가 없다.**

| 지금 되는 것 | 지금 안 되는 것 |
|---|---|
| 대시보드 · TOP5 · 카테고리 그리드 · 차트 · 검색 · 챗봇 · 즐겨찾기(브라우저 저장) | 로그인 · 회원가입 · 게시판 글쓰기 · Q&A 작성 · 자료 업로드 · AI Agent 등록 요청 전송 · 관리자 콘솔 |

안 되는 쪽은 전부 `api/*` 호출이고, 코드가 부르는 엔드포인트는 **62개**다(부록 A).
`index.standalone.html` 은 그 자리에 샘플 데이터를 채워 넣어 화면만 온전히 보이게 한 사본이다.

그래서 "서버화" 는 두 단계로 나뉜다.

- **1단계 — 정적 호스팅**: URL 하나로 모두가 본다. 화면·둘러보기는 완전히 동작.
  글쓰기·로그인은 여전히 안 됨. **오늘 안에 가능.**
- **2단계 — 백엔드**: 위 62개 API 를 구현해야 한다. 별도 개발 과제.

## 1. 지금 당장, 승인 없이 자체 공유하기

> **지금 쓰는 PC 로 먼저 시험해 보려면** — 항목별 리허설 절차가 따로 있다:
> **[로컬-PC-리허설-체크리스트.md](./로컬-PC-리허설-체크리스트.md)**
> (회사 정책 확인 · 동료 접속 검증 · 같은 출처 제약 체험 · 새 PC 신청 근거 만들기)

### 1-A. 팀 VM 또는 여유 PC 에서 정적 서버 띄우기 ★ 가장 현실적

파일 하나만 올리면 되고, 설치도 거의 없다.

> **어느 파일을 올릴지 주의.** 백엔드가 **없는** 지금 단계에서는
> `index.standalone.html` 이 맞다 — 게시판·Q&A 자리에 샘플이 채워져 화면이 온전히 보인다.
> 반대로 **나중에 백엔드를 붙이면 반드시 원본 `index.html` 로 교체해야 한다.**
> standalone 은 로더 함수를 데모 데이터로 덮어쓰기 때문에, 그대로 두면 백엔드를 다
> 만들어도 게시판이 계속 샘플만 보여준다.
> 자세한 내용은 [온프레미스-서버-구축-절차.md 제약 2](./온프레미스-서버-구축-절차.md) 참고.

**Windows 라면 IIS 가 이미 들어 있다 ★ 가장 확실**

Python 설치도 다운로드도 필요 없다. **HTTP Range 를 기본 지원**해서 V4-2 영상도
문제없고, 새 PC 의 최종 구성과도 같다.

1. 폴더를 만들고 받은 HTML 을 **`index.html` 이라는 이름으로** 넣는다
   (`MAPS-V4-2-standalone.html` 그대로 두면 IIS 기본 문서로 안 잡힌다)
2. `제어판 → 프로그램 → Windows 기능 켜기/끄기 → 인터넷 정보 서비스` 체크
3. `IIS 관리자 → 사이트 → Default Web Site → 기본 설정` 에서 실제 경로를 그 폴더로
4. `http://localhost/` 확인 → 방화벽 인바운드 80 허용 → 동료에게 `http://내IP/`

단계별 화면과 막혔을 때 대처는
[로컬-PC-리허설-체크리스트.md 경로 A](./로컬-PC-리허설-체크리스트.md) 에 있다.
**관리자 권한이 필요하다.** 권한이 없으면 같은 문서 경로 C 를 본다.

**Python 이 깔려 있다면**

```bash
py tools\serve_local.py      # Windows — python3 가 아니라 py 또는 python
python3 tools/serve_local.py  # macOS · Linux
```

받은 파일이 스크립트 하나뿐이어도 된다. 같은 폴더에 `index.html` 을 두면 그 폴더를 서빙한다.

> ⚠ **`python -m http.server` 는 쓰지 말 것.**
> **HTTP Range 요청을 지원하지 않는다**(Range 헤더를 보내도 `200 OK` + 전체 본문).
> V4-2 히어로는 3초 지점으로 **seek** 해서 3~8초만 반복하는데, Range 가 없으면 그
> seek 이 어긋난다. 같은 파일 · 같은 폴더로 서버만 바꿔 실측:
>
> | 서버 | Range | `currentTime` 범위 | 구간 이탈 |
> |---|---|---|---|
> | `python -m http.server` | `200`(무시) | 0.31~8.06초 | **6회 — 깨짐** |
> | `tools/serve_local.py` | `206` | 3.31~8.02초 | **0회 — 정상** |
>
> IIS · nginx · Docker nginx 는 Range 를 기본 지원하므로 문제없다.

**Docker 가 있으면 한 줄**

```bash
docker run -d --name maps -p 8080:80 \
  -v /srv/maps:/usr/share/nginx/html:ro nginx:alpine
```

**공통 확인 사항**

- 방화벽에서 해당 포트 **인바운드 허용** (Windows 방화벽 → 인바운드 규칙 → 포트)
- 사내 IP 로 접속 → `http://10.x.x.x:8080`
- **그 장비가 켜져 있어야 한다.** 개인 PC 면 절전·재부팅 시 끊긴다 → 팀 VM 을 권함
- 서비스로 등록해 두면 재부팅 후에도 자동으로 뜬다
  (IIS·Docker 는 기본 자동, Python 은 작업 스케줄러나 `nssm` 필요)

### 1-B. 공유 폴더에 두기

`\\서버\공유\maps\index.html` 에 두고 경로를 알려주는 방식.

- 장점: 아무 설정도 필요 없다
- 단점: `file://` 로 열려서 **일부 동작에 제약**이 생기고, 사람마다 "내 PC 에
  복사본" 을 만들게 되어 결국 버전이 갈린다. 임시 방편으로만 쓸 것

### 1-C. 지금처럼 파일 전달

가장 큰 문제는 **버전 갈림**이다. 수정할 때마다 전원에게 다시 뿌려야 하고,
누가 어떤 버전을 보고 있는지 알 수 없다. 1-A 로 옮기는 것을 권한다.

### 참고 — SharePoint · Teams · Confluence 는 기대와 다를 수 있다

- **SharePoint 문서 라이브러리에 올린 HTML 은 브라우저에서 렌더링되지 않고
  다운로드되는 경우가 많다** (보안 설정에 따라 다름). 먼저 한 개 올려서 확인할 것
- **Teams 탭**은 "웹사이트" 탭에 **URL 을 꽂는** 방식이라, 결국 1-A 가 먼저 필요하다
- **Confluence** 는 HTML 매크로가 관리자에 의해 막혀 있는 경우가 흔하다

## 3. 백엔드까지 — 로그인 · 게시판 · Q&A 를 실제로 돌리려면

정적 호스팅만으로는 안 된다. `api/*` 62개(부록 A)를 구현해야 한다.

### 3-A. 범위 판단

한 번에 다 만들 필요는 없다. 실효가 큰 순서:

1. **`data/dashboards.json` 만 서버에 두기** — API 가 아니라 **정적 JSON 파일 하나**다.
   이것만 올려도 대시보드 목록이 실데이터로 돌고, 관리자가 파일만 고치면 반영된다.
   **1단계에서 바로 할 수 있고 비용이 0 이다.** 여기부터 시작할 것
2. 공지(`api/notice`) · 게시판 읽기(`api/posts`, `api/post`) — 읽기 전용이면 구현이 가볍다
3. 로그인(`api/me`, `api/login`) — 사내 SSO 연동
4. 쓰기 계열(글쓰기 · 댓글 · Q&A · 자료 업로드 · 등록 요청)
5. 관리자 콘솔(승인 · 계정 관리 · 팝업 · 매뉴얼)

### 3-B. 스택

사내 표준을 따르는 것이 가장 안전하다. 참고 조합:

| 스택 | 적합한 경우 |
|---|---|
| Node.js + Express + SQLite/PostgreSQL | 프런트와 같은 언어. 소규모에 가장 빠름 |
| Python + FastAPI + PostgreSQL | 사내에 Python 자산이 많을 때 |
| Java + Spring Boot | 사내 표준이 Java 일 때. 인증·감사 연동이 수월 |

### 3-C. 인증은 자체 회원가입보다 사내 SSO 를

현재 코드에는 회원가입 → 관리자 승인 구조가 들어 있는데, 실제 운영에서는
**계정·비밀번호 관리 부담과 보안 책임**이 그대로 따라온다.
사내 **AD/LDAP · SAML · OIDC** 연동으로 바꾸면 그 부담이 사라지고,
"누가 썼는지" 감사도 자동으로 남는다. 백엔드 착수 시 가장 먼저 결정할 항목이다.

### 3-D. 함께 준비해야 하는 것

파일 업로드 저장 위치 · 백업 주기 · 로그 보관 · 장애 시 연락 체계.
게시판과 자료공유가 들어가는 순간 **운영 업무**가 된다.

## 4. 사내 클라우드에서 배경 영상이 버벅이는 문제

### 4-A. 왜 로컬에서는 멀쩡한데 사내 클라우드에서만 끊기나

원격 데스크톱 계열(VDI · DaaS)은 **화면을 실시간으로 인코딩해 전송**한다.
비용은 `변하는 픽셀 면적 × 변하는 빈도` 에 비례한다.

- 정지 화면 → 전송량 거의 0
- **전체 화면 배경 영상 → 매 프레임 화면 전체가 바뀐다**

실측(1440×832 표시 기준): 영상이 만드는 화면 갱신량은 **초당 약 73 메가픽셀**이다.
같은 화면이 정지해 있으면 0 에 가깝다. 이 차이가 로컬과 사내 클라우드의 차이다.

여기에 **스크롤이 겹치면 최악**이다. 원격 프로토콜이 화면 이동과 영상 변화를
동시에 인코딩해야 한다. VM 은 대개 GPU 가 없어 디코딩·합성도 전부 CPU 다.

### 4-B. 코드에 이미 반영한 것

| 조치 | 내용 |
|---|---|
| 스크롤 중 일시정지 | 스크롤이 시작되면 영상을 세우고, 멈춘 뒤 0.18초에 다시 튼다. 히어로를 보고 있는 동안에는 계속 재생되므로 "영상이 안 나온다"는 느낌은 없다 |
| 화면 밖 · 탭 비활성 정지 | 히어로를 벗어나면 재생하지 않는다 |
| 합성 레이어 고정 | 영상과 딤을 각각 독립 레이어로 승격(`translateZ(0)` · `contain:paint`)해 갱신 범위를 히어로 안으로 가둔다 |
| `preload` 축소 | `auto` → `metadata`. 첫 진입에 파일 전체를 끌어오지 않는다 |

**솔직한 한계**: 이 조치들은 스크롤 순간의 부담을 줄이지만, **히어로를 보고 있는
동안의 지속적인 전송량 자체는 줄이지 못한다.** 그건 아래 4-C 가 해결한다.

### 4-C. 결정적인 조치 — 영상을 사내에 두고 가볍게 재인코딩 ★

바꿀 곳은 `<source src>` **한 줄**이다.

```bash
# 3~8초 구간만 잘라 720p / 24fps / 무음으로 재인코딩
ffmpeg -ss 3 -t 5 -i video_main01.mp4 \
       -vf "scale=1280:-2,fps=24" -an \
       -c:v libx264 -profile:v high -crf 28 -preset slow -movflags +faststart \
       hero-720p.mp4
```

- `-ss 3 -t 5` — **실제로 쓰는 5초 구간만** 남긴다. 파일이 몇 배 작아진다
- `fps=24` — 초당 화면 갱신 횟수가 60 → 24 로 줄어 **원격 전송량이 직접 감소**한다
- `crf 28` — 화질을 조금 낮춰 영상 내 고주파 성분을 줄인다.
  원격 프로토콜의 압축률이 올라가 전송량이 한 번 더 준다
- `-an` — 어차피 `muted` 라 소리는 쓰지 않는다
- `+faststart` — 첫 프레임이 빨리 뜬다

만든 파일을 `index.html` 과 같은 폴더에 두고 소스를 바꾼다:

```html
<source src="hero-720p.mp4" type="video/mp4">
```

이러면 **외부 통신이 0** 이 되어 2장의 보안 검토도 함께 해결된다.

> **주의**: 이 영상은 외부 사이트의 자산이다. 사내 서버로 복사해 재배포하기 전에
> 출처와 사용 권한을 확인해야 한다. 필요하면 사내 홍보 영상이나 자체 촬영본으로
> 교체하는 편이 안전하다.

### 4-D. 그래도 부족하면

사내 클라우드 사양이 낮아 4-C 후에도 부담되면, **V4-1(별자리 히어로)** 을 쓰는 선택지가
있다. 캔버스 애니메이션이라 영상보다 화면 변화량이 훨씬 적다.

## 정리 — 권장 순서

1. **오늘**: 팀 VM 에 정적 서버를 띄우고 URL 로 공유 (1-A)
2. **이번 주**: 영상을 사내로 옮기고 재인코딩 (4-C) → 버벅임 완화 + 외부 통신 0
3. **그다음**: `data/dashboards.json` 을 서버에 두고 실데이터로 전환 (3-A-1)
4. **정식화**: 사내 웹서버 등록 + 도메인 + HTTPS (2장)
5. **별도 과제**: 백엔드 구현 — SSO 연동부터 결정 (3장)
